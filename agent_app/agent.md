“先理解数据，再理解用户，再调度能力，再持续对话”的多智能体框架。核心目标不是让某个单一模型一次性把所有事情做完，而是让不同智能体各司其职，共享同一份会话状态，这样多轮对话里就不会丢掉 CSV 画像、任务参数和历史结论。

一、整体框架思路

建议分成 5 层：

1）输入层

用户 query
CSV 文件
可选历史会话上下文

2）理解层

文件解析
CSV 画像
用户意图识别
参数抽取

3）编排层

决定调用哪个能力：预测、异常诊断、相关性分析、趋势分析、解释说明等
决定是否需要追问用户

4）任务层

预测智能体
异常诊断智能体
分析解释智能体
报告生成智能体

5）记忆与状态层

会话记忆
CSV 画像记忆
参数记忆
任务结果记忆
用户多轮追问上下文
二、推荐的智能体分工
1. 会话管理智能体（Session Agent）

它不做具体分析，只负责：

维护 thread_id / session_id
记录当前文件、当前数据集画像、当前目标任务
判断用户是不是在“继续上一次话题”
决定是否继承上一轮参数

它的作用是让系统知道：
“这轮用户说的深度分析，是继续刚才的预测任务，还是换一个新任务？”

2. CSV 画像智能体（Profile Agent）

输入：CSV 文件或 DataFrame
输出：结构化画像

画像建议包含：

列名、类型、缺失率、唯一值数、分布特征
时间列候选
目标列候选
分组列候选
数值列、类别列、文本列
异常值初判
可能的业务含义推断
列之间的相关性概览

这一步很关键，因为后面很多任务都依赖画像结果。
比如：

预测任务需要知道时间列、目标列、频率
异常诊断需要知道哪些列是连续值、哪些列是关键指标
多变量分析需要知道协变量候选
3. 意图识别与参数解析智能体（Parser / Router Agent）

它负责把用户自然语言解析成统一的任务指令，比如：

任务类型：预测 / 异常诊断 / 趋势分析 / 数据解释 / 对比分析
目标列：y
预测步长：25
时间列：date
分组列：id
协变量列：x1, x2, x3
模型偏好：如有则记录

这个智能体要特别支持两类输入：

第一类：首次提问
比如“帮我预测 y 未来 25 步”。

第二类：多轮追问
比如“再做深度分析”“把结果展开一点”“有没有异常”“继续解释一下”。

这时它不能重新从零解析，而应该：

继承上一轮已确认参数
只解析新增意图
对缺失信息进行补全或修正
4. 任务调度智能体（Orchestrator Agent）

这是整套系统的“大脑”。

它根据当前上下文决定：

是直接执行预测
还是先补充缺失参数
还是先做画像再执行
还是并行调用多个子智能体

例如：

用户说“预测 y 25步”
→ 先确认目标列与步长，再调用预测智能体
用户说“深度分析”
→ 结合上一轮预测结果，调用解释智能体 + 趋势分析智能体
用户说“检查有没有异常”
→ 调用异常诊断智能体
用户说“对比 A 和 B 两组数据”
→ 调用分组分析智能体
5. 任务执行智能体（Task Agents）

这里建议按能力拆分，而不是一个 agent 包打天下。

预测智能体

输入：

CSV 画像
目标列
时间列
预测步长
协变量
历史上下文

输出：

预测值
趋势总结
置信/不确定性说明
分阶段分析
业务解释
异常诊断智能体

输入：

目标列或重点指标
时间序列数据
阈值或统计规则
历史模式

输出：

异常点
异常区间
可能原因
是否是突变、漂移、波动异常
数据解释智能体

负责把模型输出翻译成用户能看懂的语言：

趋势说明
风险提示
业务含义
建议动作
报告生成智能体

负责把多个分析结果整合成完整报告，适合：

周报
会议材料
数据分析结论
业务建议
三、核心关键：统一状态对象

这套系统能不能支持多轮对话，关键不在于“有没有记忆”三个字，而在于有没有一份统一的会话状态。

建议维护一个状态对象，里面至少包括：

session_id
csv_profile
dataset_id
current_task
confirmed_spec
last_user_query
last_agent_result
dialogue_history
clarification_pending
analysis_artifacts

其中最重要的是：

1）csv_profile

这是文件画像，应该长期保留在当前会话里。

2）confirmed_spec

这是已确认的任务参数，比如：

target_column = y
prediction_length = 25
time_column = date

这份东西不能只存在对话文本里，一定要单独存结构化对象。

3）current_task

记录当前处于：

画像阶段
参数确认阶段
预测阶段
异常诊断阶段
深度解释阶段

这样后续用户说“继续”“展开”“再分析”，系统知道是在原任务上继续。

四、多轮对话怎么设计才不丢上下文

多轮对话建议分三种情况处理。

情况 1：延续同一个任务

例如：

“预测 y 未来 25 步”
“再做深度分析”
“把后 10 步重点解释一下”

处理方式：

直接复用 confirmed_spec
不重新问目标列和步长
只解析新增要求
情况 2：修改部分参数

例如：

“不是 y，改成 z”
“预测步长改成 50”
“用另一列做目标”

处理方式：

更新 confirmed_spec
保留原会话其他字段
重新进入任务执行
情况 3：开启新任务

例如：

“顺便看看异常点”
“再做一个分组对比”
“改成诊断模式”

处理方式：

保留 CSV 画像
新建 current_task
共享数据，但任务上下文重置
五、推荐的执行流程

你这套系统可以这样跑：

第一步：接收输入
用户 query
CSV 文件
第二步：数据画像
自动识别列类型
生成画像摘要
存入会话状态
第三步：意图解析
识别任务类型
提取目标列、步长、时间列等
如果缺失，进入追问
第四步：任务编排
根据意图选择预测/异常/分析等 agent
若是多轮追问，优先继承 confirmed_spec
第五步：任务执行
运行具体分析
输出结构化结果
第六步：结果解释
让解释智能体把结果转成人类可读内容
第七步：更新记忆
将本轮确认参数、结论、用户偏好写回会话状态
六、我建议你特别重视的 4 个设计点
1）不要只存“对话文本”，要存“结构化状态”

对多轮任务来说，最容易出问题的就是只保存 messages，最后模型看见一堆文本，但不知道哪些是已确认参数。

2）不要让每个 agent 各自维护自己的记忆

要有统一 session store。
否则预测 agent、解析 agent、异常 agent 会各说各话。

3）“深度分析”这种追问要当作 follow-up intent

它不是新任务，而是基于上轮结果继续分析。
所以一定要让 router 识别“延续性语义”。

4）画像与任务分离

CSV 画像是“数据层记忆”，
任务参数是“业务层记忆”，
两者分开存，后续扩展最稳。

七、你可以直接采用的框架抽象

可以把系统抽象成下面这个逻辑：

用户输入 → 意图识别 → CSV画像 → 参数补全 → 任务路由 → 子智能体执行 → 结果解释 → 状态回写

这会比“一个大模型一直聊天”稳定很多，也更适合后面扩展新功能。
